# NestJS TypeORM - Setup and Configuration

Bringing TypeORM into a NestJS codebase involves two distinct layers. First, you have `typeorm` itself, which handles the database driver, query generation, and entity mapping. Second, you have `@nestjs/typeorm`, an integration wrapper. This wrapper bridges the ORM and the NestJS Dependency Injection (DI) container, turning database connections and repositories into injectable providers.

The configuration splits into two phases deliberately. You configure the database connection once at the application root, and you explicitly declare which tables are accessible within each feature module. This enforces strict domain boundaries.

## Required Packages

A standard NestJS SQLite setup requires four specific packages.

```bash
npm install @nestjs/typeorm typeorm better-sqlite3
npm install -D @types/better-sqlite3
```

- `@nestjs/typeorm`: The NestJS integration module.
- `typeorm`: The core ORM library.
- `better-sqlite3`: The modern, high-performance, synchronous SQLite driver for Node.js. It avoids the event-loop overhead of legacy asynchronous drivers.

## Root Configuration: Bootstrapping the Connection

The application needs a single connection pool to SQLite. We define this in the root `AppModule` using `TypeOrmModule.forRoot()`. This method runs exactly once during application startup.

```typescript
// src/app.module.ts
import { Module } from "@nestjs/common";
import { TypeOrmModule } from "@nestjs/typeorm";

@Module({
  imports: [
    TypeOrmModule.forRoot({
      type: "better-sqlite3",
      database: "data/boardgames.sqlite",
      entities: [],
      synchronize: true,
      logging: false,
      enableWAL: true,
      statementCacheSize: 100,
    }),
  ],
})
export class AppModule {}
```

Explanation of the specific options:

- `entities`: An array of class references (our first example). TypeORM builds its internal schema representation from these classes. If an entity is not listed here, TypeORM does not know the table exists.
- `synchronize`: When set to `true`, TypeORM compares your TypeScript entities against the actual Postgres schema on boot. It automatically generates and executes `CREATE` `TABLE` or `ALTER TABLE` statements to make the database match your code. **Keep this disabled in production**. It can and will drop columns silently if you rename a property in your code, resulting in catastrophic data loss. We rely on migrations for production schema changes.
- `logging`: Prints the exact SQL queries generated by the ORM to the console. Toggle this on when a query performs poorly and you need to inspect the generated `JOIN`s.
- `enableWAL` & `statementCacheSize`: These enable Write-Ahead Logging and query caching. This allows SQLite to handle multiple concurrent readers and writers without locking the database, a crucial setting for web servers.

## Feature Scoping: Domain Boundaries

Opening a connection pool does not automatically make the database accessible to your services. NestJS enforces module encapsulation. A service inside `BoardgameModule` cannot magically query the `Boardgame` table; it must be granted permission.

You provide this access using `TypeOrmModule.forFeature()`.

```typescript
// src/boardgames/bordgames.module.ts
import { Module } from "@nestjs/common";
import { TypeOrmModule } from "@nestjs/typeorm";
import { Boardgame } from "./boardgame.entity";
import { BoardgameService } from "./boardgame.service";

@Module({
  imports: [TypeOrmModule.forFeature([Boardgame])],
  providers: [BoardgameService],
})
export class BoardgameModule {}
```

This call registers a `Repository<Boardgame>` specifically within the scope of `BoardgameModule`. By splitting the configuration, NestJS ensures that if you create another module later, lets say an `InvoicingModule`, it cannot accidentally mutate `Boardgame` records unless you explicitly import that entity into its scope.

## Excursion: Asynchronous Configuration for Remote Databases

While SQLite only requires a local file path, production applications frequently connect to remote database clusters like PostgreSQL. Hardcoding connection credentials in `AppModule` is a critical security failure. Applications must pull credentials from environment variables.

NestJS provides the `@nestjs/config` package to manage these variables. Because the application must parse the `.env` file before attempting to establish a network connection to the database, we replace `forRoot` with `forRootAsync`.

```typescript
// src/app.module.ts
import { Module } from "@nestjs/common";
import { TypeOrmModule } from "@nestjs/typeorm";
import { ConfigModule, ConfigService } from "@nestjs/config";
import { Boardgame } from "./boardgame/boardgame.entity";

@Module({
  imports: [
    ConfigModule.forRoot(),
    TypeOrmModule.forRootAsync({
      imports: [ConfigModule],
      inject: [ConfigService],
      useFactory: (config: ConfigService) => ({
        type: "postgres",
        host: config.get<string>("DB_HOST"),
        port: config.get<number>("DB_PORT"),
        username: config.get<string>("DB_USER"),
        password: config.get<string>("DB_PASSWORD"),
        database: config.get<string>("DB_NAME"),
        entities: [Boardgame],
        synchronize: false,
      }),
    }),
  ],
})
export class AppModule {}
```

The `useFactory` function guarantees that the DI container resolves the `ConfigService` completely before TypeORM attempts to establish the Postgres connection pool.

> _Don't forget to add the correct driver (e.g., `npm install pg`) when working with PostgreSQL_
